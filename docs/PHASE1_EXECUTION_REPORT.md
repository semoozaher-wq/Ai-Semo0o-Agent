# تقرير الفحص والتنفيذ — المرحلة الأولى

**المشروع:** `Ai-Semo0o-Agent`  
**النطاق المنفّذ:** تشغيل فعلي + تعديل ملفات فعلي + Git + تحقق موثّق + استرداد ذاتي محدود + بوابة صلاحيات  
**الحالة:** **مكتمل تقنيًا ومتحقق منه** ضمن نواة تشغيل Node مستقلة وآمنة نسبيًا.

> تطبيق Expo/React Native لا يستطيع — ولا ينبغي أن يستطيع — تشغيل طرفية أو الوصول إلى نظام الملفات الأصلي مباشرة من المتصفح أو الهاتف. لذلك وُضعت القدرة الفعلية في Runtime خادمي/محلي مستقل، بينما يبقى العميل واجهة لا تستقبل هذه الصلاحيات مباشرة.

## 1. ملخص تنفيذي

كان المشروع يوفّر واجهة ومساحة عمل **افتراضية** ومحاكاة لأدوات التنفيذ، لكنه لم يوفّر مسارًا حقيقيًا وآمنًا لتشغيل الأوامر أو تعديل مشروع على القرص. كما كانت أوامر الجودة الأساسية غير مكتملة أو مكسورة:

| بند خط الأساس | النتيجة قبل الإصلاح | الحالة النهائية |
| --- | --- | --- |
| `npm install` | نجح؛ كشف 30 تنبيهًا تبعيًا | نجح |
| `npm test` | لا يوجد script باسم `test` | ناجح: 80 فحص Harness + 6 اختبارات Runtime |
| `npm run build` | لا يوجد script باسم `build` | ناجح: تصدير Expo Web و17 مسارًا ثابتًا |
| `tsc --noEmit` | 8 أخطاء استيراد/أنواع | ناجح بلا أخطاء |
| `npm run lint` | أخطاء barrel exports وتحذيرات أسلوب | ناجح بلا أخطاء أو تحذيرات |
| `npm run doctor` | أمر `expo-doctor` غير مثبت | ناجح: 21/21 فحصًا |

## 2. ما تم بناؤه فعليًا

### نواة تنفيذ حقيقية

أضيف `execution-core/engine.mjs`، وهو Runtime مستقل يعمل داخل Node على نسخة المشروع الموجودة فعليًا على القرص.

- **TerminalSandbox**
  - يشغّل البرامج المسموح بها فقط: `npm` و`npx` و`node` و`git`.
  - يستخدم `spawn` مع `shell: false`، لذلك لا يمرّر سلسلة أوامر إلى shell.
  - يفرض timeout، حدًّا أقصى للمخرجات، وعلى Linux يطبّق حدود CPU والذاكرة عبر `prlimit`.
  - يسجّل exit code وsignal والزمن والمخرجات المقيّدة وحالة الحدود لكل أمر.

- **RealWorkspace**
  - يقرأ ويكتب ويحذف ملفات حقيقية تحت Workspace واحد محدد.
  - يمنع المسارات المطلقة و`..` والخروج من الجذر.
  - يمنع العبور عبر symbolic links.
  - يستخدم كتابة ذرّية: ملف مؤقت ثم `rename`.
  - يطبّق Patch آمنًا عبر مقارنة pre-image بالكامل؛ أي اختلاف يوقف العملية بـ `PATCH_CONFLICT`.

- **RealGit**
  - يدعم `status` و`diff` و`branch` و`checkpoint` (commit) و`rollback`.
  - لا يستعمل rollback أمر `git clean`، فلا يحذف ملفات المستخدم غير المتتبعة تلقائيًا.

- **Verification + Evidence**
  - لا ترجع معاملة التنفيذ بالحالة `verified` إلا إذا نجحت كل أوامر التحقق فعليًا بلا timeout ولا اقتطاع للمخرجات.
  - يحتفظ Runtime بـ `manifest.json` و`verification.json` و`result.json` و`git.diff` في دليل أدلة مستقل.

- **Self-Healing / Replan**
  - عند فشل عملية أو تحقق، يعيد Runtime فقط الملفات التي لمسها الوكيل إلى حالتها السابقة.
  - يمرّر تحليل فشل منظّم إلى callback اختياري لإعادة التخطيط.
  - الحد الأقصى للمحاولات من 1 إلى 5؛ لا توجد إعادة لا نهائية.

- **Permission Gateway**
  - افتراضيًا: منع كامل.
  - كل عملية محمية تطلب قدرة صريحة: `workspace.read` و`workspace.write` و`terminal.execute` و`git.read` و`git.write` و`network.access`.
  - سجل الموافقة محفوظ ضمن أحداث التنفيذ.

### واجهة تشغيل CLI

أضيف `scripts/agent-runtime.mjs` لتشغيل المعاملات على مشروع حقيقي، مثل:

```bash
node scripts/agent-runtime.mjs \
  --workspace /absolute/path/to/project \
  --plan ./plan.json \
  --allow workspace.read,workspace.write,terminal.execute,git.read,git.write
```

وتوجد أمثلة صيغة الخطة وآليات Git والأدلة في:

- `docs/PHASE1_EXECUTION_RUNTIME.md`

## 3. إصلاحات الجودة المرافقة

- إضافة `test` و`test:legacy-harness` و`test:execution` و`build` إلى `package.json`.
- إضافة `tsx` لتشغيل harness الموجود فعليًا، و`expo-doctor` لتصحيح أمر التشخيص المعلن في README.
- إصلاح مسارات الأنواع الخاطئة في مجلد `data/` الجذري.
- إصلاح خريطة أيقونات فئات الأدوات الناقصة (`github` و`zip`).
- حذف مرجع `useRouter` غير المعرّف وغير المستخدم.
- إزالة تصادم تصدير `LLMProvider` من barrel الخاص بخدمات AI.
- تسوية تحذيرات ESLint الخاصة بأنماط المصفوفات والاستيرادات غير المستخدمة.
- إضافة `.gitignore` لـ `node_modules` و`.expo` وأدلة الأدلة `.semo0o-evidence`.
- تحديث مخرجات `dist/` بعد نجاح build بحيث تطابق الشيفرة الحالية.

## 4. أدلة التحقق النهائي

نفذت الأوامر فعليًا مع timeout خارجي، وكلها انتهت بـ exit code `0`:

| الأمر | الدليل |
| --- | --- |
| `npm test` | 80/80 في harness، و6/6 اختبارات Node للنواة الجديدة |
| `npm run typecheck` | TypeScript بلا أخطاء |
| `npm run lint` | ESLint بلا أخطاء أو تحذيرات |
| `npm run build` | Expo Web export ناجح و17 مسارًا ثابتًا |
| `npm run doctor` | 21/21 checks passed |
| `npm run validate:pain-map` | نجح |
| `git diff --check` | لا توجد أخطاء whitespace |

كما نُفّذ CLI الجديد فعليًا على هذا المستودع لتنفيذ `git status` مع منح `git.read`. سجّل Runtime أن timeout وحدود المخرجات والذاكرة والـCPU كلها مفعّلة، وأن الأمر انتهى بـ exit code `0`.

## 5. نتائج التدقيق والمخاطر المتبقية

### مرتفع — تبعيات الإنتاج

`npm audit --omit=dev` ما زال يبلّغ عن **30 تنبيهًا**: **19 عاليًا** و**11 متوسطًا**، ولا توجد حرجة. تظهر السلسلة عبر Expo/Metro/React Native، ومن أمثلتها `node-forge` و`braces` و`micromatch` و`query-string` وحزم Metro.

لم أستخدم `npm audit fix --force`؛ لأن تقرير npm يقترح تغييرات major وغير متوافقة ظاهريًا (مثل الرجوع إلى Expo 44 أو React Native 0.72) وقد تكسر Expo SDK 57. المعالجة الصحيحة في المرحلة التالية هي ترقية Expo وReact Native وExpo Router عبر مسار SDK متوافق، ثم تشغيل حزمة التحقق الكاملة مجددًا.

### مرتفع — مفاتيح API في متصفح الويب

الإعدادات تحفظ `apiKeys` ضمن `AppSettings`، وطبقة التخزين تستخدم `localStorage` على الويب. أي JavaScript يعمل ضمن نفس الأصل أو XSS ناجح قد يصل إلى هذه المفاتيح. لا ينبغي اعتبار هذه البنية مناسبة لمفاتيح إنتاجية.

**التوصية:** نقل مفاتيح المزودين إلى backend/secret manager، أو استخدام OAuth/رموز قصيرة العمر؛ وعلى native استخدام تخزين آمن خاص بالمنصة بدلاً من الذاكرة فقط.

### معماري — مسار واجهة Expo الحالي

المساحة الحالية في واجهة Expo ما زالت تمثّل ملفات افتراضية، وبعض أدوات `agent-engine` الافتراضية هي محاكاة للواجهة. النواة الجديدة هي المسار الفعلي الموثّق؛ يجب ربطها في الإنتاج عبر API خادمي موثّق أو تشغيل CLI محلي مصرح به. لا يجب منح تطبيق الويب وصولًا مباشرًا إلى terminal أو filesystem لتحقيق هذا الربط.

## 6. قرار المرحلة الأولى

**القرار: جاهزة كمكوّن Execution حقيقي قابل للاستخدام من CLI أو Backend موثوق.**

لا يُوصى بالنشر الإنتاجي مع مفاتيح API مخزنة في `localStorage` أو مع التنبيهات التبعية الحالية دون خطة ترقية متوافقة. هذه نقاط المرحلة التالية، وليست سببًا لتزييف حالة نجاح المرحلة الأولى.
