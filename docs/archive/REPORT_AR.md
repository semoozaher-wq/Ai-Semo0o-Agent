## الحكم العام

المشروع **نواة قوية وتجريبية متقدمة** لمنصة وكلاء ذكاء اصطناعي عربية أولًا، وليس منتج SaaS جاهزًا للنشر العام بعد. قوته الأساسية ليست في واجهة Expo وحدها، بل في فصل Runtime حقيقي يعمل عبر Node عن عميل React Native/Expo، ثم إضافة طبقة Phase 2 تشمل مخطط مهام، ذكاء المشروع، RAG، ذاكرة مستمرة، وكيل متصفح عبر CDP، وتخزينًا محليًا للمنصة.

النتيجة العملية للمراجعة جيدة من ناحية صحة الكود الأساسي: الاختبارات نجحت، وفحص TypeScript وESLint وبناء الويب نجحوا. في المقابل، توجد حدود إنتاجية واضحة: لا يوجد Backend HTTP دائم أو نظام مصادقة متعدد المستأجرين، تخزين Phase 2 ما زال JSON محليًا، اختبار المتصفح Contract Test وليس E2E على Chrome حي، كما أن `npm audit --omit=dev` أظهر 30 ثغرة تبعية، منها 19 عالية و11 متوسطة.

**التقييم المختصر:**

- **جودة التنفيذ الحالي:** جيدة إلى جيدة جدًا كنواة هندسية.
- **الأمان في Runtime:** جيد نسبيًا بفضل default-deny، allow-list، منع traversal، وحدود الموارد.
- **نضج Phase 2:** متقدم كنواة Backend/domain library، لكنه غير مكتمل كمنصة إنتاج.
- **جاهزية النشر العام:** غير موصى بها قبل معالجة التبعيات، المصادقة، العزل التشغيلي، وإدارة الأسرار.

## ما هو المشروع؟

يعرّف README المشروع باعتباره منصة عربية RTL لبناء وتشغيل وكلاء مستقلين، مع متجر للوكلاء، محادثة متعددة النماذج، تحليل كود، تحليل ملفات، تحليلات، ووكيل BodyMap Pain. الواجهة مبنية بـ Expo وReact Native وTypeScript وتستهدف الويب وiOS وAndroid من قاعدة كود واحدة [1].

البنية المعلنة تفصل بين أربع طبقات رئيسية:

1. **واجهة التطبيق:** مسارات Expo Router وشاشات لوحة التحكم والمتجر والمحادثة والوكلاء والملفات والإعدادات.
2. **الخدمات والبيانات:** أنواع المجال، Zustand، الثيم، كتالوجات الوكلاء والأدوات والنماذج والصلاحيات.
3. **Runtime فعلي:** `execution-core/engine.mjs` لتشغيل الأوامر والتعامل مع الملفات وGit ضمن Workspace محدد.
4. **Phase 2:** `phase2-core/platform.mjs` و`phase2-core/browser-agent.mjs` لتخطيط المهام وذكاء المشروع وRAG والذاكرة والمنصة ووكيل المتصفح [2].

## البنية التقنية

يستخدم المشروع Expo `57.0.26`، وReact Native `0.86.3`، وReact `19.2.3`، وTypeScript `6.0.3`، وExpo Router `57.0.24`، وZustand `5.0.15`، و`react-native-svg` `15.15.4` [3].

يوجد في `package.json` فصل واضح نسبيًا بين أوامر التشغيل والتحقق:

- `npm test` يشغل Harness TypeScript ثم اختبارات Node.
- `npm run test:phase2` يشغل اختبارات Phase 2 مباشرة.
- `npm run typecheck` يشغل TypeScript دون إخراج.
- `npm run lint` يشغل ESLint عبر Expo.
- `npm run build` يصدّر نسخة الويب الثابتة.
- `npm run doctor` يشغل Expo Doctor.
- `npm run validate:pain-map` يتحقق من بيانات الخريطة التشريحية [3].

## تقييم Phase 2

### 1. Dynamic Planner وDAG

`TaskGraph` يبني رسمًا بيانيًا للمهام مع `dependsOn`، ويتحقق من المراجع المفقودة والدورات. الدالة `ready()` تعيد المهام التي اكتملت تبعياتها، بينما `executeTaskGraph()` ينفذ دفعات متوازية فقط عند عدم وجود تعارض في موارد القراءة والكتابة.

هذا تصميم صحيح ومفيد كبداية؛ فهو أفضل بكثير من قائمة خطوات خطية بلا اعتماديات. كما أن التنفيذ يملك حدًا للمحاولات ويدعم `replan` بدل إعادة المحاولة بلا نهاية. ويُرجع فشلًا صريحًا عندما تبقى عقد محجوبة أو تفشل عقدة نهائيًا.

**ملاحظة تصميمية:** الـ Planner الحالي ليس LLM Planner عامًا. `TaskGraph.fromGoal()` يعتمد على قواعد نصية بسيطة لاستخراج كلمات مثل browser وsearch وRAG، ثم يبني قالبًا ثابتًا. لذلك هو Dynamic DAG جيد، لكنه ليس بعدُ مخططًا دلاليًا قادرًا على فهم أي مهمة معقدة.

### 2. Project Intelligence

`buildProjectIntelligence(root)` يفحص ملفات JavaScript/TypeScript، ويستخرج:

- قائمة ملفات المصدر.
- الرموز Functions/Classes/Interfaces/Types/Enums/Variables.
- import graph وdependency graph.
- ربطًا مبدئيًا بين ملفات الاختبار والمصادر المستوردة.
- مصدر التحليل: `typescript-ast` عند توفر TypeScript أو `lexical-fallback` عند عدم توفره [2].

استخدام TypeScript Compiler API عند توفرها قرار هندسي جيد؛ فهو أكثر موثوقية من regex وحده. أما fallback فهو مفيد للبيئات التي لا تتوفر فيها حزمة TypeScript، لكنه يجب أن يبقى موضحًا للمستهلك، وهو ما يفعله الحقل `parser`.

**الحد:** Test Mapping ليس تغطية Runtime، ولا يثبت أن الاختبار نفّذ المصدر أو غطى فروعه. هو mapping ساكن مبني على imports فقط.

### 3. RAG وEmbeddings

طبقة RAG تحتوي على chunking قابل للضبط، وembeddings محلية حتمية مبنية على hashed tokens، وVector Store مستمر بصيغة JSON، واسترجاع cosine، ثم reranking بسيط يعتمد على تداخل الكلمات. يوجد adapter HTTP لمزوّد embeddings متوافق مع OpenAI دون تخزين المفتاح داخل السجل [2].

هذا مناسب كـ fallback قابل للتجربة والاختبار، لكنه ليس بديلًا عن embedding model دلالي في نظام إنتاج. الـ hashed-token vectors لا تفهم المعنى أو المرادفات جيدًا، والـ reranker الحالي lexical وليس ML reranker.

### 4. الذاكرة المستمرة

`ProjectMemory` يخزن سياق المشروع، المهام، حالات الفشل، الأحداث، والتاريخ. الاسترجاع يعتمد على مطابقة tokens داخل JSON للأحداث السابقة. هذا يكفي كذاكرة تشغيلية بسيطة، لكنه ليس ذاكرة دلالية ولا يملك سياسات عمر/حذف/حجم أو عزلًا بين المستخدمين والمشاريع.

### 5. Browser Agent

`BrowserAgent` يتصل بـ Chrome DevTools Protocol عبر WebSocket مُعطى مسبقًا، ويدعم التنقل والنقر والكتابة والتمرير واستخراج DOM والتقييم ولقطات الشاشة والتقاط أحداث Console وNetwork والتحقق المخصص. لا يدير كلمات المرور ولا تسجيل الدخول تلقائيًا، ويعتمد على جلسة CDP مصرح بها من الخارج [2].

أثناء المراجعة تم إصلاح سلوك حقيقي في `waitForLoad()`: كان من الممكن أن يعيد حدث تحميل قديم نتيجة نجاح بعد تنقل جديد. أصبح الانتظار الآن مرتبطًا بتسلسل تحميل جديد. كما أصبح `close()` يرفض الأوامر المعلقة بدل ترك Promises معلقة.

**الحد المهم:** الاختبار الحالي يثبت عقدة API والتهيئة، لكنه لا يشغّل Chrome/Chromium حيًا ولا يثبت E2E على موقع حقيقي. توثيق المرحلة يذكر هذا القيد صراحة [2].

### 6. PlatformStore وAgentPackageStore

`PlatformStore` يوفر تخزينًا محليًا لكيانات المستخدمين والمشاريع ومساحات العمل وتشغيلات الوكلاء والسجلات والاستخدام ومفاتيح API. لا يحفظ المفتاح نفسه، بل يخزن SHA-256 وآخر أربعة أحرف فقط. `AgentPackageStore` يدعم التثبيت والتحديث والتحقق من الصلاحيات والاعتماديات والإلغاء والرجوع إلى نسخة سابقة.

تم تحسين طبقة Phase 2 أثناء المراجعة في نقطتين reliability مهمتين:

- استبدال الكتابة المباشرة بكتابة ذرّية إلى ملف مؤقت ثم `rename`.
- عدم تحويل JSON التالف بصمت إلى حالة فارغة؛ أصبح تلف persistence يرفع خطأ واضحًا `PERSISTENCE_INVALID_JSON`.

هذه التحسينات في التنفيذ نفسه، وليست workaround داخل الاختبارات.

**الحد الإنتاجي:** JSON المحلي ليس قاعدة بيانات معاملات. لا توجد معاملات، أو locking بين عمليات متعددة، أو migrations، أو تشفير at rest، أو auth/authorization، أو rate limiting، أو HTTP API دائم. وثيقة Phase 2 تذكر أن هذه الطبقة Domain Store محلي وليست SaaS multi-tenant production API [2].

## Runtime والتنفيذ الآمن

يحتوي المشروع على Runtime مستقل في `execution-core/engine.mjs`. أهم ضماناته:

- بوابة صلاحيات default-deny.
- allow-list للأوامر `git` و`node` و`npm` و`npx`.
- تشغيل عبر `spawn` مع `shell: false`.
- timeout وحد أقصى للمخرجات.
- حدود CPU والذاكرة على Linux عبر `prlimit`.
- منع المسارات المطلقة و`..` وعبور symbolic links.
- كتابة ذرّية وsafe patch يعتمد على مطابقة pre-image.
- rollback لا يستخدم `git clean`، فلا يحذف الملفات غير المتتبعة تلقائيًا.
- أدلة تشغيل تشمل manifest وresult وverification وdiff.
- إعادة تخطيط محدودة بعد الفشل، مع استعادة الملفات التي لمسها الوكيل فقط [4].

هذا الجزء من المشروع هو أقوى جوانبه الأمنية نسبيًا. لكن وجود آليات الحماية داخل مكتبة Node لا يعني أن المنتج أصبح sandbox أمنيًا كاملًا ضد خصم قوي. يجب تشغيله بحساب منخفض الصلاحيات، وداخل حاوية أو VM مناسبة عند التعامل مع كود غير موثوق، مع عزل الشبكة ونظام ملفات مؤقت وسياسة موارد مستقلة.

اختبارات Phase 2 تغطي DAG والتوازي والتراجع، Project Intelligence، RAG والتخزين والاسترجاع، adapter للـ embeddings، الذاكرة، Platform Store، صلاحيات الحزم والrollback، عقدة Browser Agent، انتظار تحميل جديد، ورفض JSON التالف.

الاختبارات مستقلة في حدودها الحالية وتستخدم مجلدات مؤقتة لاختبارات persistence. لا يوجد اعتماد على خدمة خارجية؛ اختبار embedding البعيد يستبدل `fetch` داخل الاختبار بعقدة HTTP محلية deterministic، ولا يضع مفتاحًا فعليًا.

## المخاطر والقيود

### عالية الأولوية

**1. ثغرات الاعتماديات.** نفذ `npm audit --omit=dev` على النسخة المفحوصة وأظهر 30 تنبيهًا: 19 عاليًا و11 متوسطًا، دون تنبيهات حرجة. المصدر المعلن في تقرير المرحلة الأولى يربط جزءًا منها بسلسلة Expo/Metro/React Native، ويحذر من استخدام `npm audit fix --force` لأنه قد يفرض ترقيات أو تغييرات major غير متوافقة [4]. يجب إعداد ترقية Expo SDK متوافقة، ثم إعادة تشغيل الاختبارات كاملة.

**2. غياب Backend إنتاجي ومصادقة.** Phase 2 ليست API متعددة المستخدمين. لا ينبغي كشف PlatformStore أو Browser Agent أو Execution Runtime مباشرة للويب دون طبقة مصادقة وتفويض وتدقيق ومحددات موارد.

**3. الأسرار في العميل.** README يذكر إعداد مفاتيح مزودي النماذج، بينما تقرير المرحلة الأولى يوضح أن إعدادات التطبيق تحفظ `apiKeys` في `localStorage` على الويب، وهو غير مناسب لمفاتيح إنتاجية [4]. يجب نقل الأسرار إلى backend/secret manager أو استخدام OAuth/tokens قصيرة العمر، مع تخزين آمن على native.

### متوسطة الأولوية

**4. JSON persistence.** الكتابة الذرّية تمنع الملفات الجزئية، لكنها لا تحل التزامن أو المعاملات أو migrations أو corruption recovery الكامل. يلزم SQLite أو PostgreSQL أو مخزن معاملات عند تعدد المستخدمين أو العمليات.

**5. Browser E2E.** وجود CDP adapter واختبار العقدة لا يكفي لإثبات العمل مع Chrome الحقيقي، أو صفحات SPA، أو iframes، أو سياسات CSP، أو حالات navigation الفاشلة. ينبغي إضافة E2E مع Chrome/Chromium مُثبت ومشهد محلي deterministic.

**6. Planner محدود دلاليًا.** `fromGoal()` قالب rule-based. الاسم Dynamic Planner صحيح من ناحية DAG والتوازي، لكنه لا يعني وجود تخطيط عام بقدرات نموذج لغوي.

**7. الفرق بين توثيق README والنتيجة الحالية.** README يذكر Web export من 16 مسارًا ثابتًا، بينما البناء الفعلي في هذه المراجعة صدّر 17 مسارًا. هذه ليست مشكلة تشغيلية، لكنها عدم اتساق توثيقي يجب تصحيحه.

### مخاطر المجال الطبي

BodyMap Pain يجب أن يبقى تعليميًا، مع مراجعة طبية للمحتوى، ومصادر واضحة، وعدم تقديم تشخيص أو توصية علاجية جازمة. هذا متسق مع تنبيهات README و`CONTRIBUTING.md` [1] [5].

## ما تم إنجازه في هذه المراجعة

تم تعديل التنفيذ الفعلي، لا الاختبارات فقط:

1. إصلاح انتظار `BrowserAgent` لحدث تحميل جديد بدل إعادة استخدام حدث قديم.
2. جعل `BrowserAgent.close()` يرفض الأوامر المعلقة وينظفها.
3. إضافة persistence helpers داخل `platform.mjs` للقراءة الصريحة والكتابة الذرّية.
4. رفض ملفات JSON التالفة بدل إخفاء الخطأ وإعادة تعيين الحالة بصمت.
5. إضافة اختبارين سلوكيين مستقلين يغطيان الإصلاحين.
6. إعادة تشغيل الاختبارات والفحوص والبناء، ثم تنظيف مخرجات البيئة المحلية من diff.

## خطة الأولويات المقترحة

1. **ترقية dependency stack** ضمن مسار Expo SDK متوافق، ثم إعادة `npm audit` و`npm test` و`typecheck` و`lint` و`build`.
2. بناء Backend موثق ومصادق عليه يربط العميل بالـ Runtime، مع authorization على مستوى المستخدم والمشروع والقدرة.
3. تشغيل Execution Runtime داخل sandbox أقوى من مجرد allow-list، مع مستخدم منخفض الصلاحيات وعزل الشبكة والموارد.
4. استبدال JSON persistence بقاعدة بيانات معاملات عند الانتقال إلى تعدد المستخدمين.
5. نقل مفاتيح API خارج `localStorage` وعدم إرسالها إلى العميل.
6. إضافة E2E حقيقي لـ Browser Agent عبر Chromium محلي وموقع اختبار داخلي.
7. توسيع Planner من قواعد كلمات إلى طبقة تخطيط قابلة للتحقق، مع schema للخطط وحدود تكلفة ومخاطر.
8. تحديث README ليطابق العدد الفعلي للمسارات، وشرح الفرق بين واجهة المحاكاة وRuntime الفعلي.
9. إضافة CI تمنع الدمج عند فشل الاختبارات أو ظهور ثغرات عالية غير مبررة.

## الخلاصة

المستودع ليس مجرد واجهة شكلية؛ يحتوي على Runtime فعلي وحزمة Phase 2 ذات تصميم واضح واختبارات قابلة للتشغيل. أفضل ما فيه هو الفصل بين العميل والصلاحيات الخطرة، ووجود حدود تنفيذ وRollback وأدلة تشغيل. الإصلاحات التي تمت أثناء هذه المراجعة حسّنت correctness وreliability في Browser Agent وpersistence دون تغيير APIs العامة.

لكن عبارة “منصة تنافس Manus AI” يجب فهمها كهدف معماري وتجريبي، لا كحالة إنتاجية مثبتة. لا تزال المصادقة، تعدد المستأجرين، قاعدة البيانات، إدارة الأسرار، embedding الدلالي الإنتاجي، E2E للمتصفح، وترقية الاعتماديات مسائل مفتوحة. لذلك القرار الأنسب هو: **قبول المشروع كنواة هندسية متقدمة وقابلة للتطوير، مع منع النشر الإنتاجي العام قبل معالجة المخاطر عالية الأولوية.**
